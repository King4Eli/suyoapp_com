[3] Verify socket room join/leave authorization. (2026-07-13, un-ignored per explicit instruction)
    -> was a real, severe hole: socket identity came straight from an unauthenticated handshake query param (?userID=anything), so any raw socket.io-client could connect claiming to be any user and silently receive their real-time chat notifications. On top of that, join-room/leave-room/send-to-room/send-to-user/user-event let any connected socket join arbitrary rooms and inject fabricated events into any room/user with no auth at all -- confirmed unused by the real app (only appeared in commented-out "usage examples"), so removed rather than "fixed". The HTTP side was worse: /api/realtime/broadcast (global unauthenticated broadcast to every connected client) and /pull/:userID, /pullall (unauthenticated connection/online-status disclosure) had zero auth and zero real usage -- removed.
    -> fix: api_v1/routers/realtimedata.js now runs an io.use() auth middleware that verifies the same session token/hash used by HTTP (sessions.verifyFullSession) before accepting any socket connection; the socket's userID is taken from the verified session (socket.data.userID), never from client input, and it's the only room the socket ever joins.
    -> the one real feature (relaying a "new message" notification to a match partner's socket, via POST /api/realtime/pushUser/:userID, called from mobile_frontend's SocketClient.emit right after pushConversation succeeds) now requires a valid session AND verifies the caller is an active (non-blocked) match participant with the target user before relaying -- same match_status check as pushConversation.js, so it can't be used to spam fake message notifications at arbitrary users.
    -> frontend: mobile_frontend/_app/funcs/socket_realtimeData.ts now sends auth_token/auth_hash (from sessionManager) in the socket.io `auth` handshake option instead of relying on a trusted userID query param.
    -> verified end-to-end against the running dev containers with a real socket.io-client test (minted real session tokens for two DB users, a real matches row): unauthenticated connect is rejected, a spoofed query userID is ignored in favor of the verified session identity, pushUser without auth is rejected, pushUser against a nonexistent/foreign match is rejected, and a legitimate match-partner relay actually reaches the target user's socket. /broadcast and /pull* now 404, /status still works.
    -> follow-up bug found via real 2-device testing (2026-07-13): after the fix above, the pushUser HTTP relay worked (200, correctly authorized) but the recipient's socket never received anything -- server logs showed liveSocketsInRoom=0 on every relay, and zero socket handshake attempts EVER from either real device. Root cause: mobile_frontend/_app/funcs/functions.ts read `getProfile?.user_id` to get the current user's id before calling SocketClient.connect(), but cacheStorage.getCurrentUserProfile() resolves to getProfile.js's `currentUser` shape, where the id actually lives at `.profile.id` (confirmed against the same pattern used correctly in ProfileEdit.tsx/zz_devv.tsx). So userId was always undefined and SocketClient.connect() silently never ran on either device -- a pre-existing bug, not caused by the auth work above, but it's the reason realtime never worked even before that. Fixed to `getProfile?.profile?.id`.
    -> also added verbose socket lifecycle/event logging on both sides (api_v1/routers/realtimedata.js and mobile_frontend/_app/funcs/socket_realtimeData.ts) to make the next issue (if any) visible immediately instead of needing another debugging round -- logs cover handshake attempts/rejections, connect/disconnect, every event in, and the pushUser HTTP relay's authorization result + live-socket count in the target room.
